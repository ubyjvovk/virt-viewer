## Goal
`--hotkeys=release-cursor=cmd+alt` (a binding with no non-modifier key) maps
to Control+Option on macOS, contradicting the man pages which say `cmd`
selects the Command key. Fix the second conversion table so modifier-only
`cmd` bindings mean Command on macOS, exactly like the first table already
does.

## Context
- T-0007 fixed `ctrl_key_to_gtk_key()` (first table, ~line 404): an
  `#ifdef __APPLE__` block maps `cmd`/`rcmd`/`lcmd`/… → `<Meta>` and, being
  first-match, shadows the unguarded `cmd` → `<Ctrl>` rows below it.
- It missed `spice_key_to_gdk_key()`'s table (second name→keysym table in
  the same file, near line 558): `{ "cmd", "Control_L" }`,
  `{ "rcmd", "Control_R" }` etc. are unguarded. This table is the path taken
  when a `release-cursor` binding has no non-modifier key: GTK cannot accel
  modifier-only bindings, so `virt_viewer_app_set_hotkeys()` falls through to
  `virt_viewer_app_set_release_cursor_display_hotkey()` (src/virt-viewer-app.c
  ~line 2968) and the display grab sequence is built from this second table.
- Found by stress review T-0012 (blocking 1), PM-verified.

## Required change
1. In `spice_key_to_gdk_key()`'s table, add an `#ifdef __APPLE__` block
   BEFORE the existing unguarded `cmd` rows, mirroring the first table's
   fix exactly: `cmd`/`lcmd`/`leftcmd`/`left-cmd` → `"Meta_L"`,
   `rcmd`/`rightcmd`/`right-cmd` → `"Meta_R"`. Do not remove or reorder the
   existing rows; first-match shadowing is the established pattern.
2. While there (same file, first table): wrap the now-dead non-Apple
   `{ "cmd", "<Ctrl>" }` … `{ "left-cmd", "<Ctrl>" }` block of
   `ctrl_key_to_gtk_key()` in the matching `#else` branch of the `#ifdef
   __APPLE__` you find above it, so the table carries no unreachable rows on
   macOS (stress-review finding T-0013 N10). Resulting behavior on
   non-Apple platforms must be byte-identical.
3. `tests/test-hotkeys.c`: add `"release-cursor=cmd+alt"` and
   `"release-cursor=meta"` to `test_hotkeys_good` (modifier-only bindings
   take the display-hotkey path and must produce no warning on any
   platform). If a value-level assertion of the produced keysym sequence is
   possible without adding new public API, add it; if it is not, say exactly
   why in the report instead of forcing an API change.

**Value-level assertion of produced keysym sequence — why not added**
The display-hotkey path stores its result in `VirtViewerApp`'s private struct (`priv->release_cursor_display_hotkey`) via `virt_viewer_app_set_release_cursor_display_hotkey()`, and both `spice_key_to_gdk_key()` and `spice_hotkey_to_display_hotkey()` are `static` in virt-viewer-util.c. There is no public accessor to retrieve the produced sequence. Asserting its value would therefore require new public API — explicitly out of scope for this ticket — so I did not add it. The existing `test_hotkeys_good` coverage (no warning on any platform) is retained and extended instead.
