## Goal
On macOS, show virt-viewer's menu in the global macOS menu bar (instead of
inside the window), wire the standard app menu items (About/Quit,
Cmd+Q), and handle the Dock "reopen" event — using the
`gtk-mac-integration-gtk3` library as an **optional** dependency.

## Context

  `gtk-mac-integration-gtk3`, header `<gtkmacintegration/gtkosxapplication.h>`,
  type `GtkosxApplication`. Key API: `gtkosx_application_get()`,
  `gtkosx_application_set_menu_bar(app, GTK_MENU_SHELL(menubar))`,
  `gtkosx_application_set_use_quartz_accelerators(app, TRUE)`,

  (return TRUE to block), `NSApplicationDidBecomeActive`, `NSApplicationOpenFile`
  (leave file/URL handling to T-0006 — do NOT connect it here).
- Meson: add `option('macos_integration', type: 'feature', value: 'auto',
  description: 'macOS menu bar integration (gtk-mac-integration)')`;
  in `meson.build` `dependency('gtk-mac-integration-gtk3', required:
  get_option('macos_integration'))` but only attempted when
  `host_machine.system() == 'darwin'` (on other systems force it to
  `dependency('', required: false)`); set `HAVE_GTK_MAC_INTEGRATION` in
  `conf_data`, add to `common_deps`, and conditionally add
  `src/virt-viewer-macos.c` to `common_sources`.
- New module `src/virt-viewer-macos.[ch]` (plain C, gated by

  `void virt_viewer_macos_init(VirtViewerApp *app);`

  Call sites in `virt-viewer-app.c` (after the GtkApplication is set up /

#### 1. The fix (rework item 1)

Your diagnosis is right in mechanism, but the prescription needed one
correction: **there is no GtkBox child of the window.** `src/resources/ui/virt-viewer.ui:6`
is `GtkApplicationWindow id="viewer"` and its single child is
`GtkOverlay id="viewer-overlay"` (line 12); a `GtkApplicationWindow` is a
`GtkBin`, so there is no second slot to pack into.

So the menubar is now packed as an **overlay child**:

```c
overlay = GTK_WIDGET(gtk_builder_get_object(self->builder, "viewer-overlay"));
gtk_overlay_add_overlay(GTK_OVERLAY(overlay), menubar);
```

`GtkOverlay` skips non-visible children in `size_allocate` and hidden widgets
take no input, so a permanently hidden overlay child is invisible and inert,
while `gtk_widget_get_toplevel(menubar)` now returns the `GtkWindow`.

Visibility, in this order (order matters — `gtk_widget_show_all()` is a no-op
on a widget whose `no-show-all` is already set, which would leave the mirrored
items invisible and gtk-mac-integration skips invisible items):

```c
gtk_widget_show_all(menubar);            /* items visible for the mirror */
gtk_widget_hide(menubar);                /* bar itself never drawn */
gtk_widget_set_no_show_all(menubar, TRUE); /* window's show_all won't reveal it */
```

**Action groups: both `gtk_widget_insert_action_group()` calls are removed.**
The window *is* a `GtkApplicationWindow` (`virt-viewer.ui:6`), which inserts
`"win"` into itself and `"app"` from the `GtkApplication`, and the bar now
inherits them through its parent chain — the same route the header bar
popovers already use, which is the existing proof that the inheritance works
in this window. This also removes the "riskiest assumption" I flagged in
attempt 1.

Added while in there: `virt_viewer_macos_install_menubar()` skips
`gtkosx_application_set_menu_bar()` when the requested bar is already the
mirrored one. Without it, a window that regains focus repeatedly would make
gtk-mac-integration re-add its accel group to the same `GtkWindow` — now that
`gtk_window_add_accel_group()` actually gets a valid window, that call is no
longer a harmless no-op. Also added
`g_return_if_fail(gtk_widget_get_toplevel(menubar) == GTK_WIDGET(window))` so
the packing requirement is enforced at the API boundary instead of surfacing
as the Cocoa-side CRITICAL again.

Ownership changed accordingly: the container owns the widget now, so
`g_object_ref_sink()` + `g_object_set_data_full()` became a plain
`g_object_set_data()` lookup handle.
