## Goal
Three user-reported defects on real usage of the packaged app:
(a) after entering and exiting full screen, the window title is often lost;
(b) after moving the window between monitors, the title is often lost;
(c) opening Preferences while in full screen opens it in ANOTHER full-screen
Space with no way to close it.
Run an extensive window-management test matrix against a live connected
session, reproduce all three, and land: the matrix results, minimal repro
recipes, a root cause per confirmed defect, and (if feasible) an automated
regression test. **Report and document only — do not fix product behavior
in this ticket; fixes will be follow-up tickets.**

## Context
- This host has TWO displays — monitor-move scenarios are testable. The
  bundle exists at `build/Remote Viewer.app` (rebuild with
  `bash build-aux/macos/make-bundle.sh` first so it matches the tree).
- You need a CONNECTED main viewer window, not just the connect dialog.
  No guest VMs exist here; make a dummy VNC target:
  `brew install qemu` (not installed yet), then
  `qemu-system-aarch64 -machine virt -display none -vnc 127.0.0.1:1 &`
  and launch the app against it:
  `"build/Remote Viewer.app/Contents/MacOS/remote-viewer-launcher" vnc://127.0.0.1:5901`
  (gtk-vnc is bundled; even a firmware/blank framebuffer is a live session).
  Kill qemu when done.
- Automation constraints: `screencapture` works (Screen Recording is
  granted). AppleScript/System Events needs an Accessibility grant —
  PROBE it first (`osascript -e 'tell application "System Events" to get name of first process'`);
  a prior host check succeeded, so it may be available. Use AX/System
  Events to drive clicks/keys where possible; for anything it cannot
  drive, do the GTK-programmatic equivalent from a harness, and list the
  scenarios that could not be driven under "What I could not verify".
- Two DISTINCT fullscreen entry paths exist and their interaction is a
  prime suspect for (a): the app's own fullscreen action
  (View menu / F11 → `gtk_window_fullscreen`, and upstream hides the
  header bar in fullscreen — see commit 093212d "Hide the header bar in
  full-screen mode") versus Cocoa-native fullscreen (green traffic-light
  button → new Space). Cross them.
- Relevant code: `virt_viewer_window_update_title()` and the header-bar
  show/hide logic (`src/virt-viewer-window.c`), the hidden overlay
  GtkMenuBar + gtk-mac-integration sync (`src/virt-viewer-macos.c`), and
  the Preferences dialog creation/transient-for setup (find it — likely
  `virt_viewer_app` preferences action). For (c), suspect the dialog's
  NSWindow collectionBehavior on quartz (a transient GTK dialog being
  treated as full-screen-capable primary instead of auxiliary).
- Temporary instrumentation in `src/` (e.g. logging in
  `update_title`/window-state-event to see WHICH layer loses the title:
  the string GTK holds, the CSD header-bar label, or the NSWindow title)
  is encouraged but MUST NOT be committed — dirty worktree is fine.

## Test matrix — run each scenario ≥5 times (defects are intermittent);
record per-run title state and keep screenshot evidence
1. Baseline: connect; note the title text and where it is rendered.
2. Zoom/maximize via green button (Option-click, no Space change) → restore.
3. Native fullscreen (green button) → exit via green button.
4. Native fullscreen → exit via Escape and via the menu (separately).
5. App fullscreen (F11 / View menu) → exit the same way.
6. Cross paths: enter via F11, exit via Cocoa (and vice versa).
7. Drag window display A → B, wait, check title; drag back (note scale
   factors of both displays).
8. Fullscreen on display B → exit there → drag back.
9. Minimize (⌘M) → restore from Dock.
10. Hide (⌘H) → unhide.
11. Preferences while windowed: opens as a normal dialog? closes cleanly?
12. Preferences while NATIVE fullscreen — the reported trap: document
    exactly what happens (Mission Control screenshot of the Spaces), every
    close route tried (⌘W, Escape, menu, green button, clicking the main
    Space), and whether ANY recovery exists short of killing the app.
13. Preferences while app-fullscreen (F11 path).
14. The connection-error dialog while fullscreen (same trap class?).
