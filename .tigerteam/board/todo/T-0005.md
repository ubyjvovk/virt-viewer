## Goal
On macOS, show virt-viewer's menu in the global macOS menu bar (instead of
inside the window), wire the standard app menu items (About/Quit,
Cmd+Q), and handle the Dock "reopen" event — using the
`gtk-mac-integration-gtk3` library as an **optional** dependency.

## Context
- Library: Homebrew `gtk-mac-integration` 3.0.2, pkg-config name
  `gtk-mac-integration-gtk3`, header `<gtkmacintegration/gtkosxapplication.h>`,
  type `GtkosxApplication`. Key API: `gtkosx_application_get()`,
  `gtkosx_application_set_menu_bar(app, GTK_MENU_SHELL(menubar))`,
  `gtkosx_application_set_use_quartz_accelerators(app, TRUE)`,
  `gtkosx_application_ready(app)`, signals `NSApplicationBlockTermination`
  (return TRUE to block), `NSApplicationDidBecomeActive`, `NSApplicationOpenFile`
  (leave file/URL handling to T-0006 — do NOT connect it here).
- Meson: add `option('macos_integration', type: 'feature', value: 'auto',
  description: 'macOS menu bar integration (gtk-mac-integration)')`;
  in `meson.build` `dependency('gtk-mac-integration-gtk3', required:
  get_option('macos_integration'))` but only attempted when
  `host_machine.system() == 'darwin'` (on other systems force it to
  `dependency('', required: false)`); set `HAVE_GTK_MAC_INTEGRATION` in
  `conf_data`, add to `common_deps`, and conditionally add
  `src/virt-viewer-macos.c` to `common_sources`.
- New module `src/virt-viewer-macos.[ch]` (plain C, gated by
  `HAVE_GTK_MAC_INTEGRATION` in meson so it is never compiled elsewhere):
  `void virt_viewer_macos_init(VirtViewerApp *app);`
  `void virt_viewer_macos_window_set_menubar(VirtViewerWindow *win, GtkWidget *menubar);`
  Call sites in `virt-viewer-app.c` (after the GtkApplication is set up /
  in `startup`) and `virt-viewer-window.c` (where the menubar widget is
  fetched from the builder — grep `menubar`/`top-menu` in
  `src/resources/virt-viewer.ui` and `virt-viewer-window.c`) wrapped in
  `#ifdef HAVE_GTK_MAC_INTEGRATION`.
- Behaviour to implement: hide the in-window menubar
  (`gtk_widget_hide`) when the macOS bar is active; Quit from the app menu
  routes through `virt_viewer_app_maybe_quit`-equivalent
  (`NSApplicationBlockTermination` → call the existing quit path and
  return TRUE so Cocoa does not hard-exit); About uses the existing
  about dialog action if one exists (grep `about` in virt-viewer-window.c).
- Accelerator labels: with `set_use_quartz_accelerators` GTK maps
  `<Control>` accelerators to ⌘ in the menu. Verify existing accels in
  `src/resources/*.ui` still fire; do not change their strings.
- Multiple windows: each VirtViewerWindow has its own menubar; call
  `gtkosx_application_set_menu_bar` when a window gains focus
  (`focus-in-event` / `notify::is-active`) so the bar follows the active
  window — the simplest correct approach; document it.
- Sandbox: you cannot show windows. Verify by build + unit tests + code
  reading; the QA ticket T-0009 verifies visually. Write down exactly what
  you could not verify in the report.

### Deviation from the ticket's Context — read this first

The ticket assumes there is an in-window `GtkMenuBar` to hand to
gtk-mac-integration ("grep `menubar`/`top-menu` in `src/resources/virt-viewer.ui`").
**There is none.** virt-viewer has no `GtkMenuBar` anywhere: its menus are
`GtkMenuButton` popovers in the header bar / toolbar, backed by the `GMenu`
models in `src/resources/ui/virt-viewer-menus.ui` (`action-menu`,
`machine-menu`) plus a per-window, dynamically rebuilt "send key" model.

So there is nothing to `gtk_widget_hide()`. Instead each `VirtViewerWindow`
now builds an **extra, never-packed** `GtkMenuBar` over those same models
(`gtk_menu_bar_new_from_model`) and hands that to
`virt_viewer_macos_window_set_menubar()`. The ticket's declared API, the
guarding scheme and every acceptance criterion are unchanged; only the source
of the menubar widget differs. The in-window popovers are untouched, so the
GTK UI is identical on all platforms and the macOS bar is an addition, not a
replacement.

Second, smaller correction: the header is included as `<gtkosxapplication.h>`,
not `<gtkmacintegration/gtkosxapplication.h>` as the ticket states —
`gtk-mac-integration-gtk3.pc` puts `${includedir}/gtkmacintegration` itself on
the include path, so the qualified form does not compile (verified: it failed
in the first build, log `.tigerteam/logs/tests/20260830-130627-4069.log`).

  `gtk_widget_insert_action_group(menubar, "win"/"app", …)` is what makes the
  items live, relying on GTK3's action-muxer walking `gtk_menu_get_attach_widget()`

  where to look first.
- `gtkosx_application_ready()` is called on the *first* window's menubar
  rather than in `virt_viewer_macos_init()`, because it is only meaningful
  once a menu bar exists. Deliberate; flagging it since the ticket lists it
  under init's API.

  (`/opt/homebrew/Cellar/gtk-mac-integration/3.0.2/share/gir-1.0/GtkosxApplication-1.0.gir`),
  not guessed. `NSApplicationOpenFile` is deliberately left unconnected
