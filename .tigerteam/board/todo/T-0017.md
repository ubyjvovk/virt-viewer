## Goal
Five robustness fixes in the macOS integration module, from stress review
T-0013 (B4, N7, N8, N9) plus one forward-compat hardening (from the
T-0014 triage). No behavior change in the single-window happy path.

## Context
All line numbers refer to the current `mac-port` tree. Read the whole of
`src/virt-viewer-macos.c` first; it is 339 lines.

## Required changes
1. **Dangling `virt_viewer_macos_current_menubar` (T-0013 B4, the
   important one).** The static pointer (~line 40) holds a bare reference
   to a GtkMenuBar owned by a window; secondary windows are destroyed at
   runtime (guest removes a display → `virt_viewer_app_remove_nth_window()`
   → `gtk_widget_destroy`). Nothing clears the static, so
   gtk-mac-integration is left pointing at freed memory, and an
   address-reuse can make `virt_viewer_macos_install_menubar()` (~line 270)
   early-return on pointer equality forever after. Fix with
   `g_object_add_weak_pointer()` when the static is set and
   `g_object_remove_weak_pointer()` before overwriting it; when the weak
   pointer nulls out while that bar is the installed one, re-install from
   the currently focused live window if any (the existing
   `notify::is-active` handler, ~line 329, already re-installs on focus —
   reuse that path rather than inventing a new one).
2. **NULL-GError deref one refactor away (N7).** `src/remote-viewer.c`
   ~lines 332-336 does `error->message` after
   `virt_viewer_macos_spawn_uri()` returns FALSE, but the callee's
   `g_return_val_if_fail(uri != NULL, FALSE)` path (~line 202) sets no
   error. Change the caller to `error ? error->message : "..."` (match the
   tree's existing style for this pattern).
3. **Precondition after work (N8).** In `virt_viewer_macos_spawn_uri()`,
   move the `g_return_val_if_fail(uri != NULL, FALSE)` above the
   `gtkosx_application_get_executable_path()` call so the precondition is
   checked first, like everywhere else in the tree.
4. **About item floating-ref handover (N9).** ~lines 245-251: the item is
   passed to `gtkosx_application_set_about_item()` (transfer none) while
   still floating and only `g_object_ref_sink()`ed afterwards. Sink first,
   then hand the owned reference over, so ownership is unambiguous.
5. **Forward-compat open-URL signal lookup (PM triage of T-0014).** The
   shipped gtk-mac-integration 3.0.2 emits `NSApplicationOpenFile` for both
   file and URL opens (URLs arrive as absoluteString). Its master branch
   already splits URL delivery onto a new `NSApplicationOpenURL` signal;
   when brew ships that, URL opens would silently stop reaching us. After
   connecting `NSApplicationOpenFile` (~line 260), add:
   if `g_signal_lookup("NSApplicationOpenURL", GTKOSX_TYPE_APPLICATION)`
   returns nonzero, connect the same handler to it. Comment WHY (3.0.2 vs
   master delivery — keep it to two lines). Must be a no-op with 3.0.2.
