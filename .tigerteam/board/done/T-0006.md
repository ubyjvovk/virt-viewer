## Goal
Double-clicking a `.vv` file or opening a `spice://host:port` / `vnc://` URL
(e.g. `open spice://127.0.0.1:5900`) launches or reuses Remote Viewer.app and
connects, the same way `remote-viewer <arg>` does from the CLI.

## Context
- `remote-viewer` is a `GtkApplication`; CLI args flow through
  `virt_viewer_app` local options → `remote_viewer_*` (grep `open` /
  `command-line` / `G_APPLICATION_HANDLES_OPEN` in `src/remote-viewer.c` and
  `src/virt-viewer-app.c` to find how a URI/file argument becomes a
  connection). Reuse that exact path.
- Cocoa delivers file/URL opens as Apple events. With gtk-mac-integration
  (T-0005) the `GtkosxApplication::NSApplicationOpenFile` signal delivers
  file paths; URL schemes need `kAEGetURL` handling — check whether
  gtk-mac-integration 3.0.2 forwards URLs through the same signal (read
  `$(brew --prefix)/include/gtkmacintegration/gtkosxapplication.h` and its
  docs). If it does not, implement a small Objective-C file
  `src/virt-viewer-macos-url.m` registering an `NSAppleEventManager`
  handler for `kInternetEventClass/kAEGetURL` (add `objc` language in
  `src/meson.build` darwin-gated — you may touch `src/meson.build` for this
  even though it is not in scope; say so in the report). This is the only
  place ObjC is permitted.
- `Info.plist.in`: add `CFBundleURLTypes` for schemes `spice`, `vnc`,
  `spice+unix`? (no — only `spice` and `vnc`), and `CFBundleDocumentTypes`
  for extension `vv`, UTI `org.virt-manager.virt-viewer.vv`
  (`UTExportedTypeDeclarations` conforming to `public.data`, MIME
  `application/x-virt-viewer`), role Viewer. Replace the `<!-- T-0006 -->`
  marker.
- Single-instance: opening a second URL must connect in the running app the
  way `G_APPLICATION_HANDLES_OPEN` does on Linux (D-Bus is absent on macOS,
  so GApplication uniqueness does not work; that is fine — a second process
  is acceptable; document it).
- This ticket runs UNSANDBOXED (macbuild): you may build the bundle, `open`
  it, run `open spice://127.0.0.1:1` and observe the connection-error dialog
  (which proves routing), and take `screencapture -x build/qa/T-0006-url.png`.
  Kill the app afterwards (`pkill -f 'Remote Viewer.app'`).

### Design

* A `spice://`/`vnc://` URL or a `.vv` document arrives on `NSApplicationOpenFile`. `file://` URIs are converted to native paths; everything else is passed through verbatim, so the string handed to `remote-viewer` is exactly what a CLI argument would be.
* **No connection yet** (the app is parked in `remote_viewer_connect_dialog()`'s nested main loop — including right after LaunchServices launched it *because* of the URL): the URI is written into the dialog's address entry and the entry is activated. The connection then follows the identical code path a typed-in address takes, retry-on-failure included. The dialog is located via `gtk_buildable_get_name()` on the toplevels (GTK3 stores a builder id as the buildable name, **not** as `gtk_widget_get_name()` — the first attempt used the latter and silently never matched).
* **Already connected**: `virt_viewer_macos_spawn_uri()` re-runs the bundle executable with the URI. `remote-viewer` is `G_APPLICATION_NON_UNIQUE` on every platform, so this matches Linux, where a second `remote-viewer URI` is also a second process. Documented under "Single-instance behaviour".

### For the reviewer

**1. Three pre-existing bundle defects from T-0004 were fixed in `make-bundle.sh`.** All three sat on the blocking path to AC 3/4 — the bundled app aborted before it could draw the error dialog — and each is reproducible on `tigerteam/T-0004` with `"build/Remote Viewer.app/Contents/MacOS/remote-viewer-launcher" spice://127.0.0.1:1`. Please check these closely, they are the largest part of the diff and they are not what the ticket asked for:

* *Relative module paths in the dlopen caches never worked.* T-0004's comment claims gdk-pixbuf and GTK resolve a relative `loaders.cache`/`immodules.cache` entry against the cache's own directory. They do not — both pass it to `g_module_open()`, so `dlopen()` looks for `loaders/libpixbufloader_svg.so` relative to the *working directory*. Fix: the launcher rewrites both caches into `${XDG_CACHE_HOME:-~/Library/Caches}/org.virt-manager.remote-viewer/` with absolute paths on every launch, falling back to the bundled caches if that directory is unusable. `GDK_PIXBUF_MODULE_FILE` is the only env var gdk-pixbuf 2.44 reads (no `GDK_PIXBUF_MODULEDIR`), so there is no lighter option.
* *Duplicate `LC_RPATH`.* dylibbundler leaves `libpixbufloader_svg.so` with `@executable_path/../Resources/lib/` twice. dyld tolerates that in an executable but refuses to `dlopen()` a module that has it. Fix: dedupe pass over every Mach-O in the bundle (`install_name_tool -delete_rpath` removes one copy per call).
* *Invalidated module signatures.* `codesign --deep` does not sign loose `.dylib`/`.so` files, and `install_name_tool` had invalidated the Homebrew signature on each. On arm64 dyld `SIGKILL`s the process on the first `dlopen()` of such a module (crash report: `CODESIGNING / Invalid Page`). Fix: sign every bundled `.dylib`/`.so` individually before signing the bundle.

  These were latent, not new: before the first fix no module was ever successfully `dlopen()`ed, so the second and third could not surface. The visible symptom was `Gtk:ERROR … ensure_surface_for_gicon` aborting the app the first time it needed an SVG (symbolic) icon.

**2. `src/virt-viewer-macos.c` is missing from `po/POTFILES`** — pre-existing since T-0005 (`_("About")`); my `_("Not running from an application bundle")` adds to the gap. `po/POTFILES` is out of scope, so it is untouched. `src/remote-viewer.c` is already listed, so the new `_("Unable to open %s: %s")` is covered.
