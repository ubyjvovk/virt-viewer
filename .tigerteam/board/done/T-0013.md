## Worker report

### Verdict

**Request changes.** The series builds and tests clean on macOS and the
platform guarding is, with two disclosed exceptions, correct. Four issues
should be fixed before this goes to gitlab.com/virt-viewer/virt-viewer: the
commits carry no `Signed-off-by:` but do carry a `Claude-Session:` trailer,
the in-tree Homebrew formula builds a contributor's personal GitHub fork, the
bundle's declared minimum macOS version is contradicted by the binaries it
contains, and the Cocoa menu-bar bookkeeping keeps a bare pointer to a widget
that virt-viewer destroys at runtime.

### Blocking findings

**B1 — Every commit lacks `Signed-off-by:` and carries a `Claude-Session:`
trailer instead.** `git log master..HEAD`

Upstream's DCO convention is universal (35 `Signed-off-by:` trailers in the
last 30 commits of `master`); none of the 8 commits here has one. All 8 carry
`Claude-Session: https://claude.ai/code/session_01ES5ZEu5MyJnCKQH2x5mKC4`, a
private URL that means nothing to an upstream reader and will outlive the
session. The MR is rejectable on this alone.

```sh
git log master..HEAD --format='%h|%(trailers:key=Signed-off-by,valueonly)|%(trailers:key=Claude-Session,valueonly)'
git log -30 --format='%b' master | grep -c '^Signed-off-by:'
```

**B2 — `build-aux/macos/virt-viewer.rb:4` ships a formula whose only source is
a personal fork.**

```ruby
head "https://github.com/ubyjvovk/virt-viewer.git", branch: "mac-port"
```

There is no `url`/`sha256` stable spec, so the formula can *only* build
`ubyjvovk/virt-viewer@mac-port`. Landed upstream, an in-tree formula would
build a third party's branch — and would break the moment that branch is
merged or deleted (which is what this MR is for). `docs/macos.md:189-190`
documents it in the same terms ("a head-only Homebrew formula for the
`mac-port` branch"). It should point at the upstream repository, or the
formula should be dropped from the MR.

```sh
sed -n '1,10p' build-aux/macos/virt-viewer.rb; sed -n '187,195p' docs/macos.md
```

**B3 — `build-aux/macos/Info.plist.in:36-37` declares
`LSMinimumSystemVersion 12.0`, but every Mach-O in the bundle is built for a
far newer minimum.**

The bundle produced on this host reports `minos 26.0` for the main executable
and for all 83 bundled dylibs — the deployment target is inherited from the
Homebrew bottles, which are always built for the builder's OS. The `12.0`
figure is not derived from anything in the build and is not mentioned anywhere
in `docs/macos.md`.

Failure scenario: a user on macOS 12–25 downloads the DMG. LaunchServices
consults `LSMinimumSystemVersion`, sees `12.0`, and allows the launch; dyld
then aborts the process with "building for macOS-x.y but attempting to link
… built for macOS 26.0". The plist's only job here is to prevent exactly that
dialog-free failure.

```sh
bash build-aux/macos/check.sh && bash build-aux/macos/make-bundle.sh
otool -l "build/Remote Viewer.app/Contents/MacOS/remote-viewer" | awk '/LC_BUILD_VERSION/{f=1} f&&/minos/{print;f=0}'
for f in "build/Remote Viewer.app"/Contents/Resources/lib/*.dylib; do otool -l "$f" | awk '/minos/{print $2}'; done | sort -V | uniq -c
plutil -extract LSMinimumSystemVersion raw -o - "build/Remote Viewer.app/Contents/Info.plist"
```

**B4 — `src/virt-viewer-macos.c:40` keeps a bare pointer to a menu bar owned
by a window that is destroyed at runtime.**

`virt_viewer_macos_current_menubar` is a plain `static GtkWidget *` with no
weak reference. The `GtkMenuBar` it points at is an overlay child of a
`VirtViewerWindow`'s `GtkWindow` (`src/virt-viewer-window.c:574-575`), and
secondary windows are destroyed while the app runs:
`virt_viewer_app_display_removed()` →
`virt_viewer_app_remove_nth_window()` → `g_object_unref(win)` →
`virt_viewer_window_dispose()` → `gtk_widget_destroy(self->window)`
(`src/virt-viewer-app.c:1363-1367`, `src/virt-viewer-window.c:182-185`).

Nothing resets `virt_viewer_macos_current_menubar` and nothing tells
gtk-mac-integration that the menu shell it was handed is gone.

Failure scenario: a SPICE guest with two displays. Window 2 is focused, so
its bar is the installed one. The guest removes display 2; window 2 is
destroyed and the pointer dangles while `gtkosx_application_set_menu_bar()`
(`transfer none` per the GIR — the library does not own or ref the shell)
still refers to the freed `GtkMenuShell`. Any later
`gtkosx_application_sync_menubar()` / menu-bar refresh reads freed memory. In
the ABA case, GSlice hands the same address back for a new window's
`GtkMenuBar`; `virt_viewer_macos_install_menubar()` (line 270) then compares
equal, returns early, and the Cocoa menu bar is never re-pointed at the live
bar for the rest of the session.

A `g_object_add_weak_pointer()` on install (or clearing the static from a
`weak-notify`/`destroy` handler) closes both cases.

```sh
sed -n '35,48p;264,293p' src/virt-viewer-macos.c
sed -n '1348,1368p' src/virt-viewer-app.c
python3 - <<'PY'
import re;s=open('/opt/homebrew/opt/gtk-mac-integration/share/gir-1.0/GtkosxApplication-1.0.gir').read()
print(re.search(r'<method name="set_menu_bar".*?</method>',s,re.S).group(0))
PY
```

**N4 — two Linux/Windows behaviour changes inside `macos:`-prefixed commits.**
The series' stated goal is to be invisible off darwin; these are the only two
places where it is not. Both are disclosed in commit 78405fd's body but not
in its subject and not in the docs.
- `src/virt-viewer-util.c:450-456`: the `meta`/`rmeta`/`leftmeta`/… rows are
  *not* inside the `#ifdef __APPLE__` block, so `--hotkeys=release-cursor=meta+q`
  changes from "Invalid hotkey" to a working `<Meta>` binding on Linux and
  Windows. `tests/test-hotkeys.c:64` now asserts this on every platform.
- `src/virt-viewer-window.c:896-897,900-902`: adding `GDK_SUPER_MASK` to the
  modifier table changes what a pre-existing `win+X` hotkey does on Linux —
  before, it tripped `g_warn_if_fail()` and the modifier was silently dropped
  from the synthesized key sequence; now `Super_L` is actually sent to the
  guest. Arguably a fix, but it is an unannounced Linux change in a macOS
  series.

```sh
sed -n '429,458p' src/virt-viewer-util.c; sed -n '888,903p' src/virt-viewer-window.c
```

**N5 — `build-aux/macos/make-bundle.sh:117-125`: `copy_modules()` aborts the
whole script when the module directory exists but is empty.** The function is
written to warn and return 1 so the caller can skip the cache generation, but
that only covers a *missing* directory. If `$src` exists with no `*.so`, the
unquoted glob does not expand, `cp "$src"/*.so "$dst/"` fails, and `set -e`
kills the run with a bare `cp: …/*.so: No such file or directory` instead of
the intended warning. Guarding with a nullglob-style check or
`find … -exec cp` fixes it.

```sh
sed -n '117,137p' build-aux/macos/make-bundle.sh
d=$(mktemp -d); mkdir -p "$d/empty" "$d/out"; ( set -e; cp "$d/empty"/*.so "$d/out/" ); echo "exit=$?"
```

**N6 — `build-aux/macos/make-bundle.sh:365-378`: the launcher rewrites the
shared module caches on every launch, and concurrent launches are by design.**
`virt_viewer_macos_spawn_uri()` (`src/virt-viewer-macos.c:196-215`) starts a
second copy of the bundle whenever a URI arrives while a connection is up, and
`NSBundle`'s `executablePath` is the launcher, so the second process re-runs
the same `sed > "$cachedir/loaders.cache"`. `>` truncates before `sed` writes,
so the racing reader can `dlopen()` against a half-written cache. The script's
own comment (lines 213-218) explains that losing the SVG loader aborts GTK the
first time a symbolic icon is drawn. Writing to a temp file and `mv`-ing it
into place would make the update atomic.

```sh
sed -n '356,380p' build-aux/macos/make-bundle.sh; sed -n '183,215p' src/virt-viewer-macos.c
```

**N7 — `src/remote-viewer.c:332-336` can dereference a NULL `GError`.**
`virt_viewer_macos_spawn_uri()` returns `FALSE` without setting `@error` on its
`g_return_val_if_fail(uri != NULL, FALSE)` path
(`src/virt-viewer-macos.c:202`), and the caller does
`error->message` unconditionally. Not reachable today (the only caller filters
empty/NULL targets at `src/virt-viewer-macos.c:127`), but it is one refactor
away and costs one `error ? error->message : ""`.

```sh
sed -n '196,215p' src/virt-viewer-macos.c; sed -n '328,338p' src/remote-viewer.c
```

**N8 — `src/virt-viewer-macos.c:199-202`: precondition check after the work.**
`gtkosx_application_get_executable_path()` is called on line 199, before the
`g_return_val_if_fail(uri != NULL, FALSE)` on line 202. Harmless (the
`g_autofree` still frees) but inverted relative to every other
`g_return_*_if_fail` in the tree.

**N9 — `src/virt-viewer-macos.c:245-251`: the About item is handed over while
still floating.** `gtkosx_application_set_about_item()` takes the widget
`transfer none` (GIR), and it is only `g_object_ref_sink()`ed on line 251,
after the call. If the library sinks the floating reference internally the
subsequent `ref_sink` adds a second owner and the item is never finalized.
Sinking first and passing an owned reference removes the question.

**N10 — `src/virt-viewer-util.c:433-448`: seven dead table rows on macOS.**

`#ifdef __APPLE__` block above shadows every one of those keys. An
`#ifdef`/`#else` around the two blocks says the same thing without leaving
dead entries in a table a reader has to scan.

**N11 — `src/virt-viewer-util.h:52`: new exported symbol with no external
caller.** `virt_viewer_util_get_bundle_resources_dir()` is declared in the
public header and documented twice (header + `.c`), but
`src/virt-viewer-util.c` is its only user. `static` would do.
