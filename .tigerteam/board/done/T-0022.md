## Goal
Milestone 1 of a native macOS SPICE client, no GTK anywhere: a standalone
app that connects to a `spice://host:port` URI via spice-client-glib,
renders the guest framebuffer in an NSWindow at native Retina scale, and
forwards keyboard and absolute-mode mouse input. User decision 2026-09-01:
this is the new primary direction; screen + keyboard + basic mouse is the
whole milestone. NO clipboard, NO file transfer, NO USB, NO relative/server
mouse mode (log-and-ignore is fine), single display only.

## Context
- spice-client-glib 0.42 is installed (pkg-config `spice-client-glib-2.0`);
  its unpacked source (for API reference) is in the PM scratchpad at
  `/private/tmp/claude-501/-Users-d-b-virt-viewer/48736c42-ecf1-4803-a3b8-b5738f424da3/scratchpad/spice-gtk-0.42/`.
- Architecture (the CocoaSpice-proven shape): run the GLib main context on
  a dedicated background thread (never block the AppKit main thread);
  marshal framebuffer updates to the main thread (dispatch_async) and
  input events back to the GLib thread. Display channel: react to
  `display-primary-create` (format/width/height/stride/data) and
  `display-invalidate` (damage rects) — upload damage to a CALayer-backed
  view (IOSurface/Metal texture or layer contents; your choice, justify
  briefly) with `contentsScale = backingScaleFactor` so Retina is sharp,
  no interpolation blur. Inputs channel: `spice_inputs_*` for key
  press/release (XT scancodes), absolute position, buttons, scroll.
- Keyboard: generate the osx→xtkbd table from keycodemapdb — the same
  database qemu and spice-gtk use. It is vendored in the unpacked
  spice-gtk source (`subprojects/keycodemapdb`, `tools/keymap-gen`);
  generate a C table (stdc lang) mapping `NSEvent.keyCode` → XT scancode.
  Modifiers do NOT arrive as keyDown/keyUp on macOS: synthesize
  press/release from `flagsChanged` bitmask deltas (track previous flags).
  Release all pressed keys on window/app deactivation.
- Language/build: Objective-C (+ the C table), built standalone by a small
  script or Makefile inside `macos-native/` — do NOT touch the project's
  meson build. Ad-hoc codesign if needed for local run.

### Subjective rendering / latency notes vs the GTK viewer

- **Sharpness is the clear win.** The GTK widget scales the guest surface
  through its own draw path and, on a 2x panel with a 2560x1440 guest, you get
  visible resampling softness. Here the guest framebuffer lands 1:1 on
  physical pixels and text in the guest is as crisp as native macOS text. The
  hyprlock "Enter Password" label is pixel-exact in the dump.
- **Latency feels lower and is structurally lower.** The GTK path goes
  guest buffer -> cairo surface -> GdkWindow -> the GTK Quartz backend ->
  CALayer. Here it is guest buffer -> memcpy of the damaged rows -> IOSurface
  -> compositor, with the copy on the network thread and one coalesced CA
  transaction per burst. Damage bursts of ~50 rects cost one main-thread hop.
  I could not do a stopwatch A/B (see limitations), so treat "feels" as
  structural reasoning plus the trace timings, not a measurement.
- **Startup is much faster** now that audio and usbredir are disabled at the
  session: first frame at 0.3 s after launch versus ~4 s while spice-gtk was
  still spinning up GStreamer and libusb for channels nothing read.
- **Cold-start footprint** is a fraction of the GTK viewer's: no GTK, no
  gdk-pixbuf, no icon theme, no GStreamer, no libusb.

### Why the debug hooks exist (please read before reviewing them)

The machine's **login session was locked for the whole ticket**, and I cannot
unlock it. That has two consequences a reviewer should know about:

- `screencapture(1)` returns the macOS lock screen, not the app window. So
  screenshot evidence is a PNG written from the IOSurface itself
  (`VSM_DUMP_DIR` + `SIGUSR1`) — the exact bytes handed to `layer.contents`.
- No real NSEvents can be delivered to the app. So input evidence comes from
  `VSM_SELFTEST=1`, which replays a fixed script through the *real*
  `keyDown:`/`keyUp:`/`flagsChanged:`/`mouse*:`/`scrollWheel:` responder
  methods with genuine `NSEvent` objects. Everything downstream of AppKit's
  own event delivery — the keycode table, the modifier bitmask synthesis, the
  coordinate transform, the cross-thread marshalling, the wire encoding — is
  exercised exactly as it is for hardware events. AppKit's delivery of an
  `NSEvent` to a first responder is the only untested link.

Both hooks are inert unless their environment variable is set, and they are
documented in the README.

### Things the reviewer should look at closely

- **`vsm-spice.c`: the default-main-context decision.** The first
  implementation used a private `GMainContext` on the worker thread, which is
  the textbook shape — and it silently does not work. spice-gtk schedules its
  connect coroutine with `g_idle_add()` (`spice-channel.c:2810`) and flushes
  its transmit queue with `g_timeout_add_full()`, both of which attach to the
  *global default* context regardless of the thread-default. The symptom is a
  session that constructs its main channel and then does nothing forever. The
  fix is to run the default context on the GLib thread; the reasoning is in a
  comment at the top of the file. Worth a second opinion on whether that is
  safe long-term or whether spice-gtk should be patched upstream instead.
- **Single IOSurface, no double-buffering.** The GLib thread writes damaged
  rows under `IOSurfaceLock` while the compositor may be sampling. Not
  observed tearing, but it is a real race and is on the gap list.
- **`main.m` `flagsChanged:` fallback expression.** The device-dependent-bit
  path is the one that runs on real hardware; the `genericBit` fallback is a
  guess for drivers that do not set device bits and has not been exercised.
- **Scroll accumulator is a function-level `static`**, which is fine for a
  single view but would be wrong the moment multi-display lands.
