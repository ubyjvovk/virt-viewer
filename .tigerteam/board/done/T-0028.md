## Goal
Two-way plain-text clipboard between the macOS host and the guest via the
SPICE agent protocol: copy in the guest → paste on the host, copy on the
host → paste in the guest. Text (UTF-8) only.

## Context
- Read `macos-native/README.md`; prior reports in `.tigerteam/board/done/`.
- API reference: spice-gtk 0.42 source (path in T-0023's Context) —
  `SpiceMainChannel` clipboard API: `main-clipboard-selection-grab`,
  `main-clipboard-selection-request`, `main-clipboard-selection` /
  `-release` signals, and `spice_main_channel_clipboard_selection_grab/
  request/notify()`; the working reference implementation is spice-gtk's
  `src/spice-gtk-session.c`. Use
  `VD_AGENT_CLIPBOARD_SELECTION_CLIPBOARD` only (no PRIMARY on macOS)
  and `VD_AGENT_CLIPBOARD_UTF8_TEXT` only.
- Requires the guest's `spice-vdagent`. Probe first (the `agent-connected`
  property on the main channel): if the Omarchy guest has no agent, the
  code must no-op gracefully — and your evidence standard drops to
  "graceful no-op + trace", with the full flow demonstrated only if you
  can trivially enable the agent from the guest side via typed input
  (benign; do NOT install packages or reconfigure the guest beyond
  launching an already-installed agent).
- Locked decisions (PM):
  - Host→guest direction needs pasteboard-change detection; AppKit has no
    notification, so poll `NSPasteboard.general.changeCount` on a 1 s
    main-thread timer, **only while the app is active** (pause on
    resignActive). On change: grab the guest selection; send data on the
    guest's request (don't push unrequested).
  - Guest→host: on the guest's grab, request UTF8; write the received
    text to `NSPasteboard.general` (`clearContents` + `setString`).
    Guard against the echo loop: writing the pasteboard bumps
    changeCount — record the count you caused and skip it in the poller
    (spice-gtk-session has the same guard; mirror it).
  - New file `macos-native/vsm-clipboard.m` for the AppKit side; the
    spice side extends `vsm-spice.c` with main-thread callbacks +
    GLib-thread send functions following the existing marshalling
    pattern. Never log clipboard CONTENTS (lengths/types only).
- Test target `spice://100.101.77.113:5900` (disposable, benign typed
  input only; the user allows unlocking + clicking around — lock-screen
  password in root `.env` as `GUEST_UNLOCK_PW`, never echoed into
  reports/logs/commits). Full-flow evidence: type a marker string in a guest
  terminal, select/copy it (wl-copy or the terminal's copy), paste on the
  host (`pbpaste` output); reverse: `pbcopy` a marker on the host, paste
  into the guest terminal (screenshot of echo).
- Engine ceiling ≈45 min: commit early and often; hand off INCOMPLETE
  with precise next steps rather than pushing through.

### The one unmet criterion, and why

The previous attempt reported the guest→host flow as undemonstrable because the
guest's display output was off. That obstacle is gone: the display woke on real
key input, the guest was unlocked with `GUEST_UNLOCK_PW`, a terminal was opened
and both directions were driven directly. What that revealed is worse but much
more useful than "not demonstrated":

- **Guest → host:** `wl-copy guestmarkbeta` genuinely changed the guest's
  clipboard (`wl-paste` echoes it back — `guest-clipboard-after-wl-copy.png`).
  **No `main-clipboard-selection-grab` ever arrived at the client** — not one
  guest-grab line in the whole trace. `pbpaste` unchanged before and after.
- **Host → guest:** the trace shows the offer, the guest's request, and
  `host -> guest, 13 bytes`. `wl-paste` three seconds later still printed the
  *previous* value (`host-to-guest-not-landed.png`). vdagent asks for the data
  and then does not install it as the guest's selection. Note this direction was
  reported "verified" by the previous attempt — it was verified only as far as
  the wire; end-to-end it does not land either.

So the failure is symmetric and sits past the point the client controls. The
guest runs Hyprland (Wayland): `wl-copy`/`wl-paste` act on the Wayland
selection, while upstream `spice-vdagent`'s clipboard backend is X11. Xwayland
*is* running (`guest-xwayland.png`), so the likely cause is a vdagent service
with no `DISPLAY` in its environment — protocol-capable, clipboard-blind.
Fixing that means reconfiguring software inside the guest, which this ticket
explicitly puts out of scope.

### What the reviewer should look at

1. **Is the guest-side diagnosis accepted?** If yes, this ticket is done and the
   receive path stays code-reviewed but unexecuted — with no guest grab ever
   arriving, `on_clipboard_grab` → `vsm_spice_clipboard_request()` →
   `on_clipboard_data` → `-guestSentText:` has not run against a real grab. On
   a guest whose agent has a working clipboard backend, `verify.sh` plus one
   `wl-copy` closes it in a minute. If the PM would rather have that proof, the
   follow-up is a guest with an X11 desktop (or a data-control-capable agent),
   not a code change.
2. **The capability gate** (`agent_clipboard_ready()` in `vsm-spice.c`). A first
   cut grabbed as soon as `agent-connected` went true and reproducibly tripped
   spice-client-glib's own assertion, because the capability set arrives a beat
   after the connection flag. `on_agent_notify` deliberately swallows the
   not-ready-yet edge; that cannot hide a genuine absence, because the 1.5 s
   probe reports the state unconditionally.
3. **`_seenChangeCount = -1`** in `vsm-clipboard.m` makes the first poll of a
   session offer whatever is already on the pasteboard, so text copied before
   connecting reaches the guest. The cost is that every reconnect re-offers the
   current host clipboard.
4. **Echo guards** — `-guestSentText:` skips an identical write entirely and
   otherwise records the `changeCount` its own write produced. spice-gtk's
   `spice-gtk-session.c` carries the same pair.

### Out-of-scope things noticed, not touched

- **Two host-side input quirks that will bite every future `macbuild` ticket**,
  documented in section 7 of the evidence file with working helpers in
  `build/qa/` (`postkeys.c`, `type.sh`, both build artefacts, not committed):
  macOS never delivers *synthetic* modifier keys as `flagsChanged`, so
  `osascript ... using command down` sends a bare key and Super shortcuts never
  reach the guest; and `keystroke` types digits and `-` as **keypad** keycodes,
  which a guest with NumLock off reads as arrows/Home/End, silently scrambling
  any typed command. Neither affects a human pressing real keys. A
  `VSM_CLIPBOARD_SELFTEST` hook, or a general "type this ASCII string into the
  guest" helper, is worth its own ticket — it would have made this ticket's
  evidence a one-liner.
- While the input quirks were still undiagnosed, a scrambled command launched an
  interactive TUI in the guest's first terminal; `ctrl+q` did not close it and it
  may still be on the guest's workspace 1. Nothing was changed or installed in
  the guest, and the second terminal (used for all the tests above) is clean.
- The guest's display output sleeps to "Display output is not active."; real key
  input wakes it. Worth knowing before concluding a guest is dead.
