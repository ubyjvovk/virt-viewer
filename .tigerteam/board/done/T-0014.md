## Worker report

**Verdict: FUTURE WORK — 1 blocking, 3 non-blocking.** The series builds and
passes all 4 tests, the packaging/CI/shell work is high quality, and the
commits are clean and bisectable. But the headline macOS feature it exists to
deliver — opening `spice://`/`vnc://` URLs and `.vv` files from the desktop —
does not work as written, because the code connects to the wrong
`gtk-mac-integration` signal and both the code comment and `docs/macos.md`
misdescribe that library's behaviour. An upstream reviewer would (and should)
block this before merge.

### Blocking findings

1. **`spice://` / `vnc://` URL opens never deliver the URI to the handler** —
   `src/virt-viewer-macos.c:260` connects only to gtk-mac-integration's
   `NSApplicationOpenFile` signal, but that signal carries a **file path / URL
   path component**, not a URL. gtk-mac-integration 3.0.2 (the installed brew
   version, `3.0.2`) delivers `[url absoluteString]` on the **separate**
   `NSApplicationOpenURL` signal and `[url path]` on `NSApplicationOpenFile`
   (`src/gtkosxapplication_quartz.c:727,750,740,765`). For a host:port URL such
   as `spice://host:5900`, `url.path` is empty, so `virt_viewer_macos_open_file`
   hits `*target == '\0'` and returns FALSE (`src/virt-viewer-macos.c:136-138`) —
   the URL is silently dropped. The `file://` branch (line 136) is therefore
   dead for every real input: document opens arrive as plain paths (see below)
   and URL opens arrive as an empty/path-fragment string. Consequences:
   `open spice://…` and `open vnc://…` do nothing, contradicting the mission's
   criterion 3 and the section "URL and file handlers" in `docs/macos.md`.
   - Evidence (rerunnable):
     `curl -sL https://github.com/jralls/gtk-mac-integration/archive/refs/heads/master.tar.gz -o /tmp/gmi.tgz && tar xzf /tmp/gmi.tgz -C /tmp && grep -n -e 'NSApplicationOpenURL' -e 'absoluteString' -e 'url.path' /tmp/gtk-mac-integration-master/src/GtkApplicationDelegate.c`
     (shows OpenFile emitted with `url.path`, OpenURL with `absoluteString`),
     plus `grep -n 'NSApplicationOpen' src/virt-viewer-macos.c` (only
     `NSApplicationOpenFile` is connected).

2. **`NSApplicationOpenFile` does not carry a `file://` URI, so the documented
   `.vv` conversion never runs** — `src/virt-viewer-macos.c:133` claims "a file
   arrives here as a percent-encoded file:// URI" and `docs/macos.md:369-380`
   makes the same claim. In gtk-mac-integration the `application:openFile:`/
   `openFiles:` delegates forward the plain filesystem **path** (`/Users/x/a.vv`),
   and `application:openURLs:` forwards `url.path`, never `file://`. The
   `g_file_new_for_uri`/`g_file_get_path` branch (lines 136-144) can therefore
   never match a real document open. `.vv` opens appear to work only by luck of
   the else-branch: the raw path is passed through as if it were a URI and
   `remote_viewer_start()` (`src/remote-viewer.c:896-908`) happens to detect
   existing files via `g_file_new_for_commandline_arg`. This is fragile and the
   comment/docs describe behaviour the library does not have.
   - Evidence: same curl as finding 1; `grep -n 'GtkosxApplication::NSApplicationOpenFile' -A4 /tmp/gtk-mac-integration-master/src/gtkosxapplication_quartz.c` ("@path: A UTF8-encoded file path").

### Non-blocking findings

1. **Man page / behave mismatch on Linux for `meta`** — `src/virt-viewer-util.c:450-457`
   adds `meta`/`rmeta`/…→`<Meta>` **unconditionally** (outside the `#ifdef
   __APPLE__` guard that protects the `cmd`→`<Meta>` block at 427-435). On
   Linux/Windows these were previously rejected with "Invalid hotkey"; now they
   are accepted and map to `<Meta>`, a modifier GTK does not address on those
   platforms. This is a port-introduced Linux/Windows behaviour change that
   contradicts the "invisible on Linux/Windows" goal. `man/remote-viewer.pod`
   documents `meta` as a valid modifier for all platforms while only the
   macOS mapping is claimed. Low risk; consider guarding or documenting.
   - Evidence: `sed -n '407,460p' src/virt-viewer-util.c` (confirm the `meta`
     entries are after the `#endif`).

2. **`accel_key_to_keys()` widened on all platforms** — `src/virt-viewer-window.c:896-902`
   adds `GDK_META_MASK`/`GDK_SUPER_MASK` and now sends `Meta_L`/`Super_L`
   keysyms (previously `g_warn_if_fail` fired). Platform-wide, not `__APPLE__`
   gated; changes what gets forwarded to the guest for meta/super on Linux.
   Benign in practice but not platform-guarded.
   - Evidence: `git show 78405fd -- src/virt-viewer-window.c`.

3. **`spice` scheme declared with no `LSHandlerRank`** — `build-aux/macos/Info.plist.in`
   (CFBundleURLTypes) declares both `spice` and `vnc` with role Viewer and no
   rank. `vnc`'s omission is deliberate and documented (`docs/macos.md`), but
   `spice` inherits the same behaviour, so Remote Viewer is never the default
   `spice` handler even though it is the defining app for the scheme. Cosmetic
   / design; worth a one-line decision note.
   - Evidence: `grep -n -A8 'CFBundleURLTypes' build-aux/macos/Info.plist.in`.
