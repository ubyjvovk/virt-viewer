## Goal
Three user-reported defects on real usage of the packaged app:
(a) after entering and exiting full screen, the window title is often lost;
(b) after moving the window between monitors, the title is often lost;
(c) opening Preferences while in full screen opens it in ANOTHER full-screen
Space with no way to close it.

session, reproduce all three, and land: the matrix results, minimal repro
recipes, a root cause per confirmed defect, and (if feasible) an automated
regression test. **Report and document only — do not fix product behavior
in this ticket; fixes will be follow-up tickets.**

### Confirmed defects, root cause and proposed fix direction

**D1 — header bar (and therefore the title) stays hidden after a
Cocoa-initiated full-screen exit.** 5/5 (s06). Minimal recipe: connect,
press F11, click the green traffic-light button. Result: `gdkstate 0x80`
(windowed) but `hdr(vis=0,map=0)` — no title, no traffic lights, and the
window can no longer be moved or closed with the mouse.
*Root cause:* `virt_viewer_window_enter_fullscreen()` hides the header at
`src/virt-viewer-window.c:797` and `virt_viewer_window_leave_fullscreen()`
shows it at `:782`, but `VirtViewerWindow` connects no `window-state-event`
handler (`grep -n window-state-event src/` is empty), so a transition the
window server starts is never mirrored into `self->fullscreen` or the header
visibility.
*Fix direction:* connect `window-state-event` on `self->window` and, when
`GDK_WINDOW_STATE_FULLSCREEN` changes without the app having asked for it,
run the header show/hide and update `self->fullscreen` plus the `fullscreen`
GAction state. Doing it in the handler rather than in enter/leave makes both
entry paths converge, which also fixes D2. Guard it `#ifdef __APPLE__` only
if the Linux/Windows behaviour would otherwise change — the signal is
cross-platform, so an unguarded handler that simply keeps app state in sync
with reality is likely correct everywhere.

**D2 — F11 while in native full screen hides the header instead of
leaving.** 5/5 (s06b). Recipe: connect, click the green button, press F11.
*Root cause:* same desynchronisation from the other side. The `fullscreen`
GAction state is still `false` (Cocoa entered full screen without telling the
app), so F11 toggles it to `true` and calls
`virt_viewer_window_enter_fullscreen()` (`src/virt-viewer-window.c:787`) on
an already-full-screen window — hiding the header and leaving the window
full screen. *Fix direction:* subsumed by D1.

**D3 — leaving full screen restores neither size nor position; the title
bar ends up under the menu bar or on another display.** 20/20 (s03, s05,
s07b, s07c). Recipe: connect, F11, F11. Result: the window keeps
1712x1107 with origin y ≈ -23, so the client-side header bar sits behind the
macOS menu bar and no title is visible (`build/qa/s07d-topstrip.png` — GTK
still reports `hdr(vis=1,map=1,title=[QEMU (1)])`). With the external display
attached it frequently reappears at x 2673, i.e. on the other monitor.
**This is the best explanation for user report (b)**: nothing is lost when
the window is *moved* (s07, 5/5 clean, title intact across real A→B→A
drags); what the user sees is this post-full-screen jump.
*Root cause:* `virt_viewer_window_leave_fullscreen()`
(`src/virt-viewer-window.c:769-783`) clears the size request and calls
`gtk_window_unfullscreen()` but never saved or restores the pre-full-screen
frame, and `virt_viewer_display_set_fullscreen(display, FALSE)` triggers
`virt_viewer_window_resize()` (`:740-750`), which resizes the window to the
display widget's *current* natural size — still the full-screen framebuffer
allocation — plus a 2px border, which is exactly the observed 1712x1107.
I did not instrument `virt_viewer_window_resize()` to confirm the call
ordering, so treat the second half of that mechanism as strongly supported
rather than proven; the missing save/restore of the frame is certain.
*Fix direction:* record the window origin and size in
`virt_viewer_window_enter_fullscreen()` before going full screen and restore
them in `leave_fullscreen()` after `gtk_window_unfullscreen()` has settled
(on quartz that means after the state event, not synchronously), and clamp
the restored origin to the work area of the monitor it lands on so the header
bar can never end up under the menu bar.

**D4 — Preferences opened in full screen is unreachable.** 9/10 (s12
native path 4/5, s13 F11 path 5/5). Recipe: connect, enter full screen by
either route, More actions ▸ Settings…. In the 9 failing runs the dialog
survived ⌘W, Escape, a blind click at its close button, and leaving full
screen, and was still alive at the end of the run — no route tried recovered
it. s12 run 4 is the single exception and supports rather than weakens the
mechanism: there the dialog reported `activespace=1|key=1|main=1` at
`prefs-open` (it did land on the active Space), and Escape dismissed it
immediately. Evidence: `awk '/^== s12 run=4 /{p=1} /^== s12 run=5 /{p=0} p'
build/qa/results.tsv`.
*Root cause:* `src/resources/ui/virt-viewer-preferences.ui:9` sets
`<property name="type-hint">normal</property>`. GDK-quartz maps
`GDK_WINDOW_TYPE_HINT_NORMAL` to an `NSWindow` with
`NSWindowCollectionBehaviorFullScreenPrimary`; measured
`collectionBehavior = 0x8c0` (`0x800` AllowsTiling | `0x80` FullScreenPrimary
| `0x40` IgnoresCycle). Control experiment in the same process: the
connection-error `GtkMessageDialog`, which uses GTK's default dialog type
hint, measures `0x1140` (`0x1000` DisallowsTiling | `0x100`
**FullScreenAuxiliary** | `0x40`). Only an auxiliary window is allowed to
draw over another window's full-screen Space, so Preferences is left behind
on the desktop Space while the viewer owns the full-screen Space.
*Fix direction:* drop the `type-hint` override from the `.ui` (a `GtkDialog`
defaults to `GDK_WINDOW_TYPE_HINT_DIALOG`, which is what every other dialog
in the app already gets) so GDK-quartz gives it FullScreenAuxiliary. Verify
with the same instrumentation that `collectionBehavior` gains `0x100`. If
upstream needs the hint kept for a non-macOS reason, the darwin-only
alternative is to set the auxiliary collection behaviour on the dialog's
NSWindow after realize.

**D5 — ⌘W and Escape never close the Preferences dialog, even windowed.**
5/5 (s11b). The dialog is shown with `gtk_window_present()`
(`src/virt-viewer-app.c:3577`) but `isKeyWindow` is 0 in every windowed sample
until it is clicked, so the keystrokes are delivered to the viewer window.
(The one full-screen run where the dialog *did* become key, s12 run 4, is the
only observed counter-sample — see D4.) Clicking
the close button works 5/5. The connection-error dialog behaves the same way
(measured `key=0`, Escape had no effect), so this is app-wide, not specific
to the Preferences type hint. My leading hypothesis is the seat/keyboard grab
that gtk-vnc holds on the focused display widget, but I did not instrument
gtk-vnc, so the *cause* is unproven — the *behaviour* is measured and
reproducible. Worth its own follow-up ticket; it is what turns D4 from an
annoyance into a trap.

### Regression test — what is and is not automatable
`tests/test-macos-window-state.c` covers title retention across five
maximize/unmaximize cycles and passes (16.6s). It does **not** cover
fullscreen, for a concrete reason: an unbundled test binary enters native
full screen fine but never leaves — `gtk_window_unfullscreen()` produced no
`window-state-event` within a 20s wait, reproducibly, so a fullscreen cycle
in `meson test` can only time out. The bundled app does not have that
problem. Beyond that, none of D1-D4 is reachable from an in-process GTK test
at all: each needs a transition *initiated outside GTK* (the green button, or
a Space switch by the window server), and no GTK API can request one. D4 is
additionally not expressible as a passing test today — the assertion that
would guard it (`collectionBehavior` has the `0x100` auxiliary bit) fails on
the current tree, and this ticket is forbidden from fixing behaviour; the
follow-up that changes the `.ui` should add exactly that assertion.
