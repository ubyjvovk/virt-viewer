## Goal
Window chrome that makes the viewer feel like a real macOS app: native
fullscreen, an "Actual Size" command, a Send Key menu for chords the
guest needs but AppKit eats, an explicit toggle to forward ⌘ shortcuts to
the guest, and correct handling of guest resolution changes mid-session.

## Context
- Read `macos-native/README.md`; prior reports in `.tigerteam/board/done/`.
- Locked decisions (PM):
  - **Fullscreen**: native macOS fullscreen
    (`NSWindowCollectionBehaviorFullScreenPrimary`); standard View ▸
    "Enter Full Screen" item (AppKit provides `toggleFullScreen:`,
    ctrl+⌘F). In fullscreen the guest image aspect-fits with black bars
    (set the view/layer background to opaque black); the existing
    aspect-fit coordinate transform must stay correct for mouse position.
  - **View menu**: "Actual Size" (⌘0) resizes the window to guest pixels ÷
    backingScaleFactor (the launch size). Keep the existing
    aspect-ratio-locked resize behavior otherwise.
  - **Input menu**:
    - "Capture Keyboard" toggle, **default ON**, checkmark state (user
      decision 2026-09-01: the guest is Omarchy/Hyprland, bound heavily
      on SUPER, so ⌘ must reach the guest by default). While ON and a
      session is connected and the guest view is key, `VsmView`
      overrides `performKeyEquivalent:` to consume EVERY ⌘ chord —
      including ⌘Q, ⌘W, ⌘H, ⌘M, ⌘0 — and forward it as scancodes (the ⌘
      press itself already goes via flagsChanged). App shortcuts
      (⌘Q/⌘0/ctrl+⌘F…) therefore work only while capture is OFF or no
      session is connected; the menu bar stays reachable by mouse
      always — note both in the README. System-owned chords (⌘-Space,
      ⌘-Tab, screenshots) cannot be caught at this layer; that is
      T-0029, not this ticket — do not add an event tap here.
    - **Send Key submenu**: Ctrl+Alt+Del, Ctrl+Alt+Backspace, PrintScreen,
      F11 — each sends the full chord as ordered press + reverse-order
      release scancode sequence through `vsm_spice_send_key`. Items
      disabled when no session is connected.
  - **Guest resolution change**: on a `primary_create` with new
    dimensions while the window exists, update `guestWidth/Height`, the
    IOSurface binding, and the window content size (unless fullscreen —
    then just re-fit). Today the size is set once; make it re-entrant.
- **Live-target care rules**: `spice://100.101.77.113:5900` is the user's
  disposable-but-live Omarchy VM. The user has allowed unlocking it and
  clicking around ("nothing of value there"): the lock-screen password is
  in root `.env` as `GUEST_UNLOCK_PW` — type it via the viewer to unlock;
  never echo it into reports, logs, trace output, or commits. An unlocked
  Hyprland desktop gives much better evidence (real windows reacting to
  SUPER chords). Still NEVER click "Ctrl+Alt+Del" (or any
  destructive/power chord) against it. Verify the send-key mechanism with a
  harmless chord through the SAME code path (e.g. temporarily invoke the
  chord-sender with Shift+F11 from a debug call, or add a benign
  "Shift+Escape" item for the test run) plus `VSM_TRACE=1` output showing
  press order and reverse release order for the real menu items exercised
  while DISCONNECTED is not possible (items disabled) — so: benign chord
  live + trace, destructive items by code inspection. State exactly what
  was sent to the guest.
- Fullscreen + Retina: in fullscreen on the 2x panel the guest may be
  scaled; `magnificationFilter` handling already exists — just confirm
  and report how it looks.
- Engine ceiling ≈45 min: commit early and often; hand off INCOMPLETE
  with precise next steps rather than pushing through.

### For the reviewer
- `-performKeyEquivalent:` relies on AppKit offering key equivalents to the
  key window's view hierarchy before the main menu. That held in every live
  test (⌘Q, ⌘0, ⌘Return all reached the guest), but it is the one assumption
  the whole capture design rests on.
- The ⌘Q local event monitor now returns the event unhandled whenever capture
  is on, a session is live and the viewer window is key. If a future change
  lets a modal dialog coexist with a live session, that escape hatch closes —
  the condition would need revisiting.
- Gating ⌘ in `flagsChanged:` on `captureKeyboard` is slightly beyond the
  ticket's letter. Without it, using a Mac shortcut with capture off still
  pressed SUPER in the guest, which trips Hyprland; it seemed clearly within
  the spirit of "an explicit toggle to forward ⌘ shortcuts to the guest".
- Pre-existing, untouched: `-sendButton:mask:down:event:` sends the button
  even when `-guestPointFor:x:y:` rejects the position, so a click in a
  fullscreen black bar still presses at the guest's last known coordinates.
- AppKit injects "Show Tab Bar"/"Show All Tabs" into any menu titled *View*.
  They are inert; suppressing them would mean
  `NSWindow.allowsAutomaticWindowTabbing = NO`, which felt out of scope.
- Protocol slip to disclose: early in the run I used
  `pkill -x spice-viewer` once to stop a viewer whose PID I had captured
  wrongly. AGENTS.md forbids `pkill -f`; `-x` matches the exact process name,
  not the command line, so no sibling worker's `remote-viewer`/GTK process
  could match — but it is still a pattern kill and every subsequent stop used
  the exact recorded PID.
- The user was actively working on this Mac during the run; the viewer's
  `activateIgnoringOtherApps:` stole focus a few times, and a handful of their
  keystrokes reached the guest before I noticed. Nothing destructive was
  typed. That focus-stealing is pre-existing behaviour, not something this
  ticket introduced.
