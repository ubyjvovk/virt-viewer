## Goal
Make Quit work on macOS: ⌘Q, the app-menu "Quit Remote Viewer" item, and the
window close button must terminate the app both while it sits in the
connect dialog and after a (failed or live) connection.

## Context
- QA (T-0009 attempt 2, on the bundle built from `mac-port` at 15:26) found:
  with the app frontmost at the "Connection details" dialog, ⌘Q does nothing;
  AX shows *Quit Remote Viewer* and *Quit and Close All Windows* with
  `AXEnabled = false`; Escape and the close button do not exit either.
  Screenshots/report: `.tigerteam/artifacts/T-0009/` (or rebuild and repro).
- The integration lives in `src/virt-viewer-macos.c` (T-0005/T-0006):
  `virt_viewer_macos_init()` connects `NSApplicationBlockTermination` →
  `virt_viewer_app_maybe_quit()` and always returns TRUE;
  `gtkosx_application_ready()` is called from
  `virt_viewer_macos_window_set_menubar()` (first VirtViewerWindow).
- Hypotheses to test first (you are unsandboxed — build the bundle with
  `bash build-aux/macos/check.sh && bash build-aux/macos/make-bundle.sh`,
  `open` it, use `osascript`/AX if Accessibility is granted, else observe):
  1. gtk-mac-integration disables the Quit item while a GTK nested main loop
     / modal (the connect dialog, `remote_viewer_connect_dialog()`) is
     running, or until `gtkosx_application_ready()` — check whether the main
     window (created in `startup`) installs its menubar before the connect
     dialog appears; if not, call `gtkosx_application_ready()` at the end of
     `virt_viewer_macos_init()` (it is safe to call once, early).
  2. `NSApplicationBlockTermination` returning TRUE unconditionally blocks
     Cocoa; `virt_viewer_app_maybe_quit()` may be a no-op at the connect
     dialog stage (nothing started; nested loop). Decide: when no session is
     active, quit directly (`g_application_quit()` + break out of the connect
     dialog loop the way its Cancel button does — grep `remote-viewer-connect.c`
     for how Cancel ends the dialog); when a session is active, keep the
     "ask before quit" path.
  3. The window close button on the connect dialog / main window should map
     to the same quit path.
- Keep all changes inside `#ifdef HAVE_GTK_MAC_INTEGRATION` (or the macos
  module); non-darwin behaviour unchanged. Kill test processes by exact PID —

### Root cause (reproduced first, on the bundle built from this branch)

Two separate defects, both in the `NSApplicationBlockTermination` handler:

1. At the connect dialog there is no session, yet the handler called
   `virt_viewer_app_maybe_quit()`, which asks *"Do you want to close the
   session?"* — a nonsensical question with nothing connected, put up as a
   small untitled window at the top-left corner (transient for the still
   invisible main window), far from the visible dialog. Evidence:
   `build/qa/T-0010-before-quitdialog.png`.
2. Confirming it did **not** quit. `virt_viewer_app_quit()` ends in
   `g_application_quit()`, which cannot unwind the nested `GMainLoop` that
   `remote_viewer_connect_dialog()` (`src/remote-viewer-connect.c:78`) runs
   from inside `GApplication::startup`. The windows went away and the process
   stayed alive forever with no UI — verified with `ps` and `sample`
   (main thread parked in `remote_viewer_connect_dialog` →
   `g_main_loop_run`).

QA's *"AXEnabled = false"* observation did **not** reproduce here: the app
menu's Quit item reported `enabled = true` both before and after the fix (see
the criteria below), and clicking it did invoke the handler. What QA saw as
"⌘Q does nothing" is defect 1+2 above; note also that when the app is not
truly frontmost the keystroke goes elsewhere, which is easy to hit when
driving the app with `osascript` (see "For the reviewer").

Escape, the connect dialog's Cancel button and its window close button were
already fine (they cancel the dialog and the app exits) — that cancel path is
what the fix reuses.

### Files changed

- `src/virt-viewer-macos.h` — new `VirtViewerMacosCancelModalFunc` typedef and
  `virt_viewer_macos_set_cancel_modal_func()` prototype: the hook a frontend
  uses to say how to leave its nested main loop, mirroring the existing
  open-URI hook.
- `src/virt-viewer-macos.c` — `virt_viewer_macos_block_termination()` now
  splits on `virt_viewer_app_has_session()`: with a session it keeps the
  existing `virt_viewer_app_maybe_quit()` "ask before quit" path (plus a
  re-entrancy guard so a second ⌘Q does not stack a second confirmation);
  with no session it cancels any nested loop through the new hook and calls
  `g_application_quit()` directly. Cocoa's own termination is still always
  vetoed. Added the setter, documented both.
- `src/remote-viewer.c` — split `remote_viewer_find_connect_dialog()` out of
  `remote_viewer_find_connect_dialog_entry()` (same toplevel-by-builder-id
  walk, now reused) and added `remote_viewer_macos_cancel_modal()`, which
  emits `delete-event` on the live connect dialog — exactly what its Cancel
  button and close button do — so `remote_viewer_start()` returns
  "No connection was chosen" and the startup handler quits. Registered in
  `remote_viewer_init()`, inside the existing `#ifdef
  HAVE_GTK_MAC_INTEGRATION`.
- `docs/macos.md` — rewrote the "Quit / ⌘Q" bullet of "What it does" into the
  session / no-session split, and added one known limitation (see below).

No changes outside the ticket's scope; `virt-viewer-window.c` and
`virt-viewer-app.c` turned out not to need any (the window close button
already routes to the same path, and no new app-level API was needed —
`virt_viewer_app_has_session()` is already public).

Two deviations from the criterion as written, both deliberate:

- `open -a "<this bundle>" spice://…` instead of bare `open spice://…`: the
  bare form goes to whichever bundle LaunchServices has registered for the
  scheme, which on this host is another worker's/PM's copy. `-a` delivers the
  URL to *this* bundle through the same Cocoa `-application:openURLs:` path
  (confirmed: the URI landed in the connect dialog and was activated) without
  re-registering the scheme system-wide.
- the error dialog was dismissed with its window close button (via
  `System Events … click (first button of window whose role description is
  "close button")`) rather than by pressing OK. Synthetic clicks
  (`click at {x, y}`) and synthetic key presses do not reach GTK widgets in
  these dialogs — see "For the reviewer". For a single-OK
  `GtkMessageDialog` the two are equivalent: `virt_viewer_app_disconnected()`
  (`src/virt-viewer-app.c:1861`) discards the response and destroys the
  dialog either way.

### For the reviewer

- **Not runtime-verified: the live-session branch.** There is no SPICE/VNC
  server on this host (a hand-made TCP listener only ever reaches the failed
  handshake). What *was* observed is that with a session object present
  (during the "Unable to connect" dialog) ⌘Q still puts up the "Do you want
  to close the session?" confirmation, i.e. the branch is taken; and
  cancelling that confirmation correctly does not quit. The code inside that
  branch is unchanged from before apart from the re-entrancy guard.
- **Known limitation, now documented, not fixed:** ⌘Q *while* the "Unable to
  connect" dialog is still up takes the has-session branch (the failed
  session object still exists at that point), so it asks about closing a
  session that never opened; and confirming cannot take effect until that
  dialog is dismissed, after which `remote_viewer_start()` loops back to the
  connect dialog. Quitting from there then works. Fixing it properly needs a
  predicate finer than the public `virt_viewer_app_has_session()` (something
  like "connected", which has no public getter) — out of scope here.
- **Out of scope, noticed while testing:** the message dialogs raised from
  `virt_viewer_app_disconnected()` / `virt_viewer_app_simple_message_dialog()`
  never become the Cocoa key window (title bar drawn inactive, traffic lights
  grey), because their transient parent is the still-hidden main window. A
  human can click them (clicking an inactive window activates it) but no
  keyboard input reaches them, so Return/Escape/Tab do nothing and
  `osascript` cannot drive them at all. This is also why criterion 2 used the
  close button. Worth its own ticket.
- **Testing gotcha for whoever re-runs this:** `osascript … keystroke` goes to
  whatever is frontmost *at that instant*. `set frontmost of process
  "remote-viewer" to true` does not reliably stick when the machine is in
  use, and a ⌘Q that misses lands in the reviewer's own editor. Always
  activate, verify `frontmost`, and send the keystroke inside a single
  `osascript` invocation (the script quoted under criterion 1).
- `build/qa/T-0010-before-quitdialog.png` is the pre-fix screenshot of the
  misplaced "Do you want to close the session?" dialog at the connect dialog.
- Every test process was started and killed by exact PID; no `pkill` was used.
  Nothing of mine is left running (`pgrep` clean), and the temporary
  `build-nomac/` tree is gitignored.
