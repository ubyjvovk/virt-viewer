## Worker report

### Verdict

**Request changes.** The series builds and its four tests pass both with and
without gtk-mac-integration, but it has four blocking defects: modifier-only
`cmd` release hotkeys do not use Command, bundles built without the optional
integration advertise handlers they cannot service, the documented `APP_DIR`
override can recursively delete arbitrary directories, and the Homebrew
formula fetches a personal feature branch rather than the upstream project.

### Blocking findings

1. **Modifier-only `cmd` release hotkeys still mean Control, contradicting the
   new macOS semantics and documentation.** `ctrl_key_to_gtk_key()` maps `cmd`
   to `<Meta>` on macOS, but `spice_key_to_gdk_key()` still maps it to
   `Control_L`/`Control_R` at `src/virt-viewer-util.c:432` and
   `src/virt-viewer-util.c:558`. This second converter is exactly the path used
   when `release-cursor` has no non-modifier key (`src/virt-viewer-app.c:2968`).
   Thus `--hotkeys=release-cursor=cmd+alt` becomes Control+Option, while `meta`
   becomes Meta+Option, despite `docs/macos.md:461` saying `cmd` and `meta` both
   select Command. The added test uses `cmd+alt+r`, so it avoids this special
   path. Evidence: `nl -ba src/virt-viewer-util.c | sed -n '432,456p;548,586p'; nl -ba src/virt-viewer-app.c | sed -n '2951,2978p'; nl -ba docs/macos.md | sed -n '461,470p'`.

2. **A bundle built without gtk-mac-integration claims URL/document handlers
   that have been compiled out.** The dependency is optional/auto at
   `meson.build:450`, and the disabled configuration builds successfully, but
   the only remote-viewer open-event hook is inside
   `HAVE_GTK_MAC_INTEGRATION` at `src/remote-viewer.c:224`. Nevertheless every
   generated plist unconditionally declares `spice://`, `vnc://`, and `.vv`
   ownership at `build-aux/macos/Info.plist.in:50`. In that supported build,
   LaunchServices opens the app but no code consumes the Apple event; the
   claim that the disabled build is a working plain-GTK variant at
   `docs/macos.md:445` omits this functional loss. Either packaging must require
   the integration or omit/replace the declarations when it is absent.
   Evidence: `nl -ba meson.build | sed -n '450,461p'; nl -ba src/remote-viewer.c | sed -n '224,347p'; nl -ba build-aux/macos/Info.plist.in | sed -n '42,100p'; nl -ba docs/macos.md | sed -n '437,447p'`.

3. **The documented `APP_DIR` override can destroy unrelated data.** The
   `abspath()` helper accepts any absolute or source-relative path without
   canonicalization or a bundle-suffix/root safety check
   (`build-aux/macos/make-bundle.sh:25`), then
   `build-aux/macos/make-bundle.sh:82` executes `rm -rf "$APP_DIR"`. For example,
   the documented override `APP_DIR=.` resolves to the source tree and removes
   it after staging succeeds; `APP_DIR="$BUILD_DIR"` deletes the configured
   build tree. Reject unsafe targets before the recursive deletion. Evidence:
   `nl -ba build-aux/macos/make-bundle.sh | sed -n '25,35p;76,85p'`.

4. **The Homebrew formula is not upstreamable as written.** Its sole source is
   the personal fork and temporary branch
   `https://github.com/ubyjvovk/virt-viewer.git`, `mac-port`, at
   `build-aux/macos/virt-viewer.rb:4`. After this series is merged, `brew
   install --HEAD` would still fetch that external branch rather than the
   upstream GitLab repository and default branch. Evidence:
   `nl -ba build-aux/macos/virt-viewer.rb | sed -n '1,8p'`.

### Non-blocking findings

1. **The port is not behavior-invisible on Linux/Windows.** The new `meta`
   aliases are outside the Apple guard at `src/virt-viewer-util.c:450`, and the
   Meta/Super synthesis in `accel_key_to_keys()` is unguarded at
   `src/virt-viewer-window.c:896`; the portable test explicitly accepts `meta`
   at `tests/test-hotkeys.c:64`. This broadens accepted hotkeys and changes Send
   Key synthesis on every platform. Split/justify it as a cross-platform change
   or guard the macOS-only behavior. Evidence: `git diff master...HEAD -- src/virt-viewer-util.c src/virt-viewer-window.c tests/test-hotkeys.c`.

2. **The new hotkey tests prove only that parsing emits no warning, not the
   promised mappings.** `tests/test-hotkeys.c:63` feeds `cmd`/`meta` values into
   `virt_viewer_app_set_hotkeys()` and the loop at line 77 makes no assertion on
   the resulting accelerator or display grab sequence. This is why blocking
   finding 1 passes. Add platform-conditional value assertions and a
   modifier-only `release-cursor=cmd+alt` case. Evidence:
   `nl -ba tests/test-hotkeys.c | sed -n '56,81p'`.

3. **The first commit's stack-protector claim does not cover Apple silicon.**
   `meson.build:277` excludes all `aarch64` before Darwin is considered, so this
   host's successful arm64 build contains no explicit stack-protector flag even
   though commit `f4841aa` says the flags were enabled on Darwin. This is a
   commit-message/implementation mismatch, not a regression from master.
   Evidence: `nl -ba meson.build | sed -n '277,293p'; rg -n -- '-fstack-protector' build/build.ninja || true`.

4. **The app-bundle artifact step is unreachable in a clean CI job.** The only
   build step at `.github/workflows/macos.yml:25` runs `check.sh`, whose last
   actions at `build-aux/macos/check.sh:14` are compile and test; nothing calls
   `make-bundle.sh`. Consequently the `hashFiles()` condition at
   `.github/workflows/macos.yml:35` is always false on a fresh runner. Either
   build the bundle or remove the dead upload/associated claim. Evidence:
   `nl -ba .github/workflows/macos.yml | sed -n '19,40p'; nl -ba build-aux/macos/check.sh`.
