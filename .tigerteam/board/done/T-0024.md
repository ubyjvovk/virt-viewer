## Goal
Turn the PoC into an app a person can launch without a terminal: started
with no URI it shows a connect window; an auth failure prompts for a
password; a connection error or disconnect shows an alert with
Reconnect/Close instead of silently exiting. With a URI on argv, behavior
is unchanged (connect immediately).

## Context
- Read `macos-native/README.md`; T-0022/T-0023 reports in
  `.tigerteam/board/done/`.
- Locked UX decisions (PM):
  - **Connect window** (no argv URI): a small window with a URI text field
    (pre-filled from `NSUserDefaults` key `VsmLastURI`), a default
    "Connect" button (Return activates). On connect: save the URI to
    defaults, hide the connect window, proceed exactly as the argv path.
  - **Auth**: when the session fails with `SPICE_CHANNEL_ERROR_AUTH`,

  `SpiceChannel` (`channel-event` with `SPICE_CHANNEL_ERROR_AUTH`); see

  and spice-gtk's own `spice_session` usage.

### Design decisions worth reviewing

- **Session rebuild, not reuse.** Reconnect and auth-retry both do
  `stop`/`free`/`new`/`set_password`/`start`. A `SpiceSession` that has
  errored out is finished as far as spice-client-glib is concerned.
- **`vsm_spice_free()` defers the actual release to the main queue**
  (`vsm-spice.c:713`). This is the one real hazard the ticket introduced:
  `blit_damage()`, `notify_status()` and the cursor path all
  `dispatch_async` blocks that capture the `VsmSpice *` and dereference it on
  the main thread. Freeing became reachable at runtime for the first time in
  this ticket, so a queued damage block could have hit freed memory. The
  thread is joined first (nothing new can be enqueued) and the main queue is
  FIFO, so a block appended after the join runs strictly after every pending
  callback. Consequence: one struct is leaked at process exit, when the
  queue no longer drains.
- **Teardown happens before any dialog is shown.** `runModal` pumps the main
  queue, so a live session behind an alert would keep delivering callbacks
  into a half-dismantled view. `handlingDisconnect` additionally swallows the
  extra `disconnected` callbacks that sibling channels queue, which would
  otherwise stack a second alert during the first one's modal loop.
- **⌘Q needed a local event monitor** (`main.m:-installQuitMonitor`). This
  was found by testing, not predicted: AppKit disables the main menu for the
  duration of a modal session, so with only the Quit menu item ⌘Q was
  silently swallowed while the alert was up and the app stayed alive
  (measured before the fix — see below).
- **Password lifetime.** `vsm_spice_set_password()` copies the string and
  refuses to run after `start()`; the copy is applied to the session's
  `password` property on the GLib thread at session construction, and wiped
  through a `volatile char *` before `g_free()`. The AppKit-side copy is an
  `NSString` on the delegate; that one cannot be wiped, which is noted in the
  README. Nothing writes it to defaults, logs or `VSM_TRACE`.
- **Alert icons are set explicitly** (caution / lock). `NSAlert` badges the
  application icon and an un-bundled binary has none, so the default was a
  generic blue folder — visible in the pre-fix state of
  `build/qa/05-error-alert.png`'s first capture.
- **Escape on "Close"**: `NSAlert` only wires Escape to a button literally
  titled "Cancel", so the Close button's key equivalent is set by hand.

### Auth path: exactly how it was exercised

The live target has no password, and no password-protected SPICE server was
available on this host: Homebrew's qemu is built **without** SPICE support
(`qemu-system-x86_64: -spice: invalid option`), so the "run a local
password-protected server" option in the ticket was not reachable.

The prompt was therefore forced with a LOCAL, UNCOMMITTED one-line edit to
`macos-native/vsm-spice.c` — adding `auth_failed = 1;` to the
`SPICE_CHANNEL_ERROR_CONNECT` case of `on_channel_event()` — so a plain
connect failure to `spice://127.0.0.1:1` took the auth branch. Shots 08–11
are from that build. The edit was then reverted with
`git checkout macos-native/vsm-spice.c`, the binary rebuilt, and shot 12
(live argv connect) taken with the reverted binary. `grep -rn "auth_failed =
1" macos-native/*.c` in the committed tree returns only `vsm-spice.c:355`,
which is the genuine `SPICE_CHANNEL_ERROR_AUTH` case.

**What that proves:** the prompt, the secure field, the
teardown → `set_password` → rebuild → `start` retry cycle, the
prompt-reappears-on-repeat-failure loop, and the Cancel → connect-window path
all run end to end.

**What it does NOT prove:** that a server actually *accepts* a password
supplied this way. The `password` property is set on the session before
connect (`vsm-spice.c:471`) and the spice-gtk 0.42 source reads it in
`spice_channel_send_spice_ticket()` (`src/spice-channel.c:1231`), so the
plumbing is right by inspection, but it is untested against a real
password-protected server. **A reviewer with such a server should test it.**

### For the reviewer, closely

1. `vsm_spice_free()`'s deferred release (`vsm-spice.c:709-723`) — the
   reasoning above is the load-bearing part of the reconnect feature. If it
   is wrong, reconnect is a use-after-free.
2. `-[VsmAppDelegate disconnectedWithReason:authFailed:]` re-entrancy
   (`main.m`): `handlingDisconnect` + the `!self.spice` check are what stop a
   second alert from opening inside the first one's modal loop. I exercised
   the double-failure path (Reconnect on a dead port, twice) but a real
   multi-channel session dropping all channels at once would hit it harder.
3. The ⌘Q monitor swallows the event (`return nil`) for `Cmd` + `q` with no
   other modifiers. It fires ahead of the responder chain, so a guest can
   never receive ⌘Q — that was already true via the menu item, and matches
   T-0029's note that ⌘Q stays a host shortcut, but it is worth a conscious
   nod.
4. Auth against a real password-protected server (see above).
