## Goal
A double-clickable, relocatable `.app` for the native viewer: bundle
script, Info.plist with `spice://` URL scheme and `.vv` document type,
Cocoa handlers that route both into the existing connect path, ad-hoc
codesigning that survives Gatekeeper's code-signature kill.

## Context
- Read `macos-native/README.md`; prior reports in `.tigerteam/board/done/`.
- **Study the GTK port's bundler first**: `build-aux/macos/make-bundle.sh`
  solved the hard problems already — recursive dylib copy +
  `install_name_tool` rewrite, LC_RPATH dedupe, and the critical lesson
  (T-0006): **every bundled Mach-O must be codesigned AFTER the last
  install_name_tool rewrite**, or dlopen dies with SIGKILL (Code
  Signature Invalid) and the app "quits unexpectedly". This app is far
  simpler (no GTK, no pixbuf/IM caches, no GStreamer) — do NOT copy the
  cache machinery, only the dylib+sign pattern.
- Locked decisions (PM):
  - New script `macos-native/make-bundle.sh` (bash, `set -euo pipefail`,
    runs from any cwd) building `macos-native/build/SPICE Viewer.app`.
    The display name lives in ONE variable at the top (`APP_NAME="SPICE
    Viewer"`) — it is a placeholder pending a user decision; note that in
    a comment.
  - Info.plist: `CFBundleIdentifier` `io.github.virt-viewer.spice-viewer`
    (placeholder, single variable), `NSHighResolutionCapable` true,
    `LSMinimumSystemVersion` matching what the binary is actually built
    for (check `vtool -show-build` / minos — the GTK port shipped a 12.0
    plist over 26.0 binaries, review finding opus B3; do not repeat it),
    `CFBundleURLTypes` for `spice` and `spice+tls`,
    `CFBundleDocumentTypes` for the `vv` extension.
  - App delegate: `application:openURLs:` and `application:openFile:` →
    if no session is connected, connect (same path as the connect
    window); if a session IS connected, show a one-button alert "Already
    connected — disconnect first" and ignore. Handlers must work both at
    launch (Finder starts the app) and while running.
  - `.vv` parsing: `GKeyFile`, group `[virt-viewer]`, honor `type`
    (must be `spice`, else error alert), `host`, `port`, `password`;
    log-and-ignore all other keys (each ignored key g_message'd once).
    Delete-on-open (`delete-this-file=1`) is honored.
  - The plain binary build (`build.sh` → `spice-viewer`) must keep
    working; make-bundle.sh may call build.sh.
- Test target `spice://100.101.77.113:5900` (disposable, benign input
  only, never hardcode the URI in committed files).
- Verification is Finder/LaunchServices-level: use `open` (the bundle,
  the URL, a .vv file), give it seconds, then check
  `~/Library/Logs/DiagnosticReports` for new crash logs (there must be
  none). Record PIDs and `kill` exact PIDs — never `pkill -f`.

### Two defects found and fixed during verification

Both are LaunchServices delivery quirks that the first implementation got wrong; both are now documented in `macos-native/README.md` ("URLs and .vv files") so they are not reintroduced:

1. Since macOS 10.13 a delegate that implements `-application:openURLs:` receives **file** opens there too, as `file://` URLs — `-application:openFile:` is never called for a Finder open. The first version handed the `file://` URL straight to the session, so every `.vv` file failed with "connection failed" (commit `8d402e3`).
2. A **bundled** app receives its command-line argument through `-application:openFile:`, not on `argv`. `spice-viewer spice://host:port` run from inside the bundle therefore reached the `.vv` parser and reported "No such file or directory" (commit `4a94af4`).

### For the reviewer

- **Naming placeholders.** `APP_NAME="SPICE Viewer"`, `BUNDLE_ID="io.github.virt-viewer.spice-viewer"`, `APP_VERSION="0.1.0"`. `BUNDLE_ID` in particular is load-bearing: LaunchServices registrations, the Accessibility (event-tap) grant and `NSUserDefaults` are all keyed on it, so it wants a decision before anything ships.
- **`delete-this-file` policy.** Honoured only when the connection is *accepted*. A file refused for the wrong `type`, or because a session is already on screen, is left on disk. The alternative (delete whenever parsed, treating the password as one-shot) is defensible; this is a judgement call worth a look.
- **`.vv` UTI is imported, not exported.** The GTK `Remote Viewer.app` exports `org.virt-manager.virt-viewer.vv` with `LSHandlerRank Owner`; two exporters would leave the Finder description up to install order. Consequence on *this* machine: several GTK bundles from sibling worktrees are registered, so a bare `open file.vv` goes to one of them. The `.vv` tests above therefore used `open -a "SPICE Viewer.app" file.vv`, which is the identical AppKit delivery (and is what "Open With" and a clean machine's double-click do).
- **`spice+tls://`** is declared and passed through unchanged; `libspice-client-glib` does understand that scheme (`strings` shows `spice+tls://`), but no TLS path was exercised — TLS is out of scope per the ticket, and a `.vv` offering only `tls-port` fails the host/port check with an alert rather than silently connecting in the clear.
- **Marker tip commit.** `f2e385e` is empty; it exists only to give the branch tip the ticket title. The work is in `f3b83f0`, `0080dca`, `8d402e3`, `4a94af4`, `163cc39` — kept unamended because the protocol forbids rewriting commits.
- **Out-of-scope observation, not touched:** the QA helper `build/qa/winlist.m` (gitignored) exists because `screencapture` of a whole display on this host captures the user's private desktop content. If the board wants repeatable native-viewer GUI evidence, promoting a window-targeted capture helper into `.tigerteam/scripts/` would be worth a ticket.
